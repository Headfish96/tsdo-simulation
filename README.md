# Kubernetes Model-Set Transition Experiments

임무 단계에 따른 이종 모델 세트 전환을 연구한 **기존 Kubernetes 실험 코드와 결과 아카이브**입니다.
순차 배포와 세트 단위 배포 요청·병렬 대기를 비교하며, 연구 설계와 실제 구현 범위를 구분해 기록합니다.

## 관련 논문

**전술 임무 단계 이종 AI 모델 세트의 오케스트레이션을 위한 쿠버네티스 커스텀 컨트롤러 설계**

최하영 · 박범식 · 백승호, 한국통신학회 2026년 하계학술대회.
[공개 논문 PDF](https://d2j16w31g89z0j.cloudfront.net/site/2026s/abs/0721-ZUPVY.pdf)

논문은 MSDO라는 아키텍처를 제안하며, 당시 실험 파일에는 TSDO라는 이름이 남아 있습니다.
이 저장소는 논문에서 제안한 전체 커스텀 컨트롤러 구현이 아니라 **Python과 kubectl을 이용한 배포 실험 프로토타입**입니다.
공동 연구이며, 이 저장소의 공개를 공동저자의 기여에 대한 독점적 주장으로 해석하지 않습니다.

## 구현 범위

| 구성 | 이 아카이브에서 확인되는 내용 |
| --- | --- |
| 워크로드 | nginx:alpine을 이용한 모의 Deployment. 실제 AI 추론 모델이 아님 |
| 기준 방식 | 기존 Deployment 삭제 후 신규 Deployment별 적용·Available 대기를 순차 수행 |
| 제안 방식 프로토타입 | 기존 세트 삭제, 신규 YAML 적용, ThreadPoolExecutor로 Available 병렬 대기 |
| 실패 경로 | 대기 실패 시 기존 YAML 재적용 시도. 실패 주입과 복구 완료 검증은 없음 |
| 커스텀 리소스 / Reconcile / 상태 머신 | 논문 설계 내용. 해당 구현 파일은 발견되지 않음 |

`kubectl apply`의 다중 문서 적용은 원자적 트랜잭션이 아닙니다. Deployment Available 대기를 실제 AI 서비스 품질·무중단 보장의 증거로 취급하지 않습니다.

## 보존 파일

```text
legacy/scripts/       기존 측정 및 그림 생성 Python 코드 3개
legacy/yamls/         기존 세트별 Deployment YAML 3개
legacy/results/       기존 10회씩의 JSON과 당시 그림 PNG 2개
tools/analyze.py      이번 정리에서 추가한 표준 라이브러리 기반 재집계 도구
tests/                재집계 도구의 검증 테스트
```

발견한 실험 코드·설정·결과 파일 10개는 바이트 단위로 원본과 동일하게 보존했습니다.
로컬 도구 설정과 작업 지시 문서는 실험 코드가 아니므로 포함하지 않았습니다.
기존 JSON에는 실행 환경, 이미지 digest, 개별 이벤트 로그가 없어 당시 실행 전체의 출처를 독립적으로 증명할 수는 없습니다.

## 기존 결과 재집계

Python 3.10 이상, 외부 패키지나 Kubernetes 접속 없이 실행 가능합니다.

```bash
python3 tools/analyze.py
python3 -m unittest discover -s tests -v
```

결과는 기존 JSON을 재계산한 값이며 새로 클러스터에서 측정한 수치가 아닙니다. 이상치를 임의로 제거하지 않고 각각 10회를 모두 포함합니다.
원본 파일 SHA-256도 출력하므로 파일 변경 여부를 확인할 수 있습니다.

| 기존 기록의 지표 | 순차 방식 | TSDO 프로토타입 |
| --- | ---: | ---: |
| 표본 수 | 10 | 10 |
| 총 전환 시간 평균 | 6.077249초 | 0.987213초 |
| 총 전환 시간 중앙값 | 5.979966초 | 0.888019초 |
| 총 전환 시간 모집단 표준편차 | 0.295977초 | 0.301271초 |

기록상 평균 총시간 차이는 83.7556%입니다. 서로 다른 처리 절차를 측정한 이 프로토타입의 관측값이며, 일반적인 Kubernetes 성능 향상률이 아닙니다.

## 반드시 알아야 할 한계

1. **실제 KEDA·Argo Rollouts 벤치마크가 아닙니다.** 기존 코드의 해당 표기는 순차 처리 모사를 뜻합니다. 경쟁 도구 전반의 성능 우위를 입증하지 않습니다.
2. **부분 전환 시간의 정의가 다릅니다.** 기준 코드는 첫 신규 Deployment 적용 후부터 마지막 Available까지, TSDO 코드는 첫 Available 관측부터 마지막 Available 관측까지를 계산합니다. 두 값의 감소율은 동일 지표 비교로 사용할 수 없습니다.
3. **논문 설계와 삭제 순서가 다릅니다.** 제안 설계는 신규 세트 준비 후 이전 세트 제거이지만, 이 실험 코드는 이전 세트를 먼저 삭제합니다. 무중단·원자적 전환을 검증한 구현이 아닙니다.
4. **수렴도 그림은 도식입니다.** `legacy/scripts/plot_results.py`는 평균 총시간에 단계 함수·시그모이드를 적용합니다. `fig_convergence.png`는 실측 시계열이 아닙니다.
5. **롤백 0회는 롤백 성공 검증이 아닙니다.** 기존 표본에서 실패 경로를 검증한 근거가 없습니다.
6. 이미지 태그가 고정 digest가 아니며, 클러스터 버전·하드웨어·캐시 조건이 저장되지 않았습니다. 동일한 시간 수치의 재현을 보장하지 않습니다.
7. 논문 초록의 83.5%와 본문의 83.8%가 다릅니다. 성능 수치는 원본 JSON의 재집계와 별개로 확인해야 합니다.

## 클러스터 실험을 다시 할 때

**원본 측정 스크립트는 현재 kubectl 컨텍스트의 Deployment를 삭제합니다. 운영·공용 클러스터에서 실행하지 마세요.**
전용 폐기 가능한 로컬 클러스터와 별도 kubeconfig에서만 검토 후 실행해야 합니다. JSON도 덮어쓰므로 아카이브를 복사한 별도 작업 폴더에서 수행합니다.

이 아카이브에는 이번에 새로 실행한 클러스터 벤치마크가 없습니다. 후속 검증에서는 양쪽에 동일한 이벤트 기반 계측을 적용하고, 실제 컨트롤러·서비스 라우팅·실패 주입을 별도로 구현해야 합니다.

## 연구에서 얻은 경험

Deployment 생명주기, 병렬 준비 대기, 세트 전환 조건과 실패 복구 설계를 다뤘습니다.
실험 결과를 코드와 함께 검토하면서 아키텍처 제안, 프로토타입 구현, 검증된 사실을 분리하는 것이 중요함을 확인했습니다.
